# Phase 1: Organisation Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Anyone in the organisation can create an account with email and password (or Google, GitHub, Microsoft), sign in, reset a password, and land straight in the organisation workspace, under an admin-controlled sign-up policy.

**Architecture:** The existing single-process server and document store stay. Sign-up policy becomes a pure module that replaces `decideRole` for the organisation workspace. Token verification gains local JWT checks (HS256 or JWKS) with the existing Supabase `getUser` call as fallback. Without Supabase, a dev auth module gives an offline email + password flow with signed tokens. The client Login page gets sign-in and create-account forms, a reset page, and a Microsoft button; the workspace switcher is hidden and sign-in opens the `hq` workspace directly.

**Tech Stack:** Node 24, TypeScript, `ws`, `@supabase/supabase-js`, `jose` (new), React 18, Vite, `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-14-relay-org-platform-design.md` (sections 7.4, 11, 12 step 1, 14, 15 items 3, 7, 10). Deactivation is already covered by the existing `removeMember` and `restoreMember` events plus the `removed` list; the admin wording changes in the admin phase. `zod` validation is introduced in the phase that adds new client events.

## Global Constraints

- Keep `npm test` and `npm run lint` (`tsc --noEmit`) green after every task. New test files are added to the `test` script in `package.json`.
- Tests use the file store only; no network. Supabase calls are behind injectable interfaces as in `server/auth.ts`.
- Document format changes are additive and filled by `normalize()` in `server/index.ts`.
- Code, comments, commits and docs are normal prose. Commit messages use Conventional Commits and end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- Sign-up acceptance rule (spec 7.4): domain in `settings.allowedDomains`, or valid invite, or org open and not invite-only. `RELAY_OWNER_EMAIL` decides the owner; before an owner exists only allowed-domain or invited sign-ups succeed. Without the var, first signer is owner and the admin console warns.
- OAuth emails count as verified only when `email_verified` is true (spec 15.7).

## Review Focus

1. Email case: `Ada@Example.COM` must match allowed domain `example.com` and must map to the same account as `ada@example.com` in dev auth. Test in Task 1 and Task 3.
2. Invite plus deactivated: a removed user with a valid invite must still be rejected. Test in Task 1.
3. Malformed JWT (wrong signature, expired, `alg: none`) must return null, never throw. Test in Task 2.
4. Dev token tampering: changing the name part of a signed dev token must fail verification. Test in Task 3.
5. Reset-password link opened while already signed in as someone else must still show the reset form for the recovery session. Covered by manual check in Task 6, step 7.
